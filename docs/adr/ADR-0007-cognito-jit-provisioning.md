# ADR-0007: 未登録Cognito Subjectの初回JIT自動登録を許容する

## 状態

採用（2026-07-27、要判断C の決定）

## 背景

`CognitoJwtAuthenticationConverter` は、未登録のCognito Subjectが初めてAPIへ到達したときに
`app_user` を自動生成し既定ロール SUPPORTER を付与する実装（JIT provisioning）になっていた。
これは標準的なOIDC統合パターンだが、「誰でもSignUpすれば即座に支援者として登録される」ことを
許容するかは業務判断が必要なため、`TODO(question)` として保留していた。

### 設計書は登録手段を定めていない

改めて確認したところ、基本設計・詳細設計のいずれにも `app_user` 行の生成手段の規定が無い。

| 観点 | 設計書の記載 |
|---|---|
| 画面 | `SCR-001 ログイン` のみ。**新規会員登録画面が無い** |
| API | `API-US-001/002`（自分のプロフィール参照・更新）、`API-AD-001/002/003`（会員検索・ロール更新・会員停止）。**ユーザー作成APIも招待APIも無い** |
| §9.1 | 「Cognito Subjectと内部UserIdを分離する」「ロールはアプリケーションDBを正とする」のみ |

つまりJITは設計書の空白を実装が埋めた状態であり、放置すると
「登録手段が存在しないサービス」か「暗黙の自動登録」かが未定のままdev環境へ出ることになる。

### インフラ側の前提

`cognito.tf` は `allow_admin_create_user_only = false`（自己サインアップ有効）、
`auto_verified_attributes = ["email"]`（メール検証必須）で構成されている。

## 選択肢

1. **JITを許容する**（現行実装を承認し、ガードを追加する）
2. JITを許容せず、管理者Invite方式へ変更する
3. 設定値でJITの有効・無効を切り替えられるようにする

## 判断

**選択肢1（JITを許容する）** を採用する。ただし後述のガードを追加する。

## 判断理由

- 支援者が自分で参加できることはクラウドファンディングの前提であり、
  権限マトリクス（基本設計 §2.2）でも SUPPORTER は公開プロジェクトの閲覧と支援申込が主で、
  事前審査を要する性質の権限を持たない。
- 選択肢2は、**設計書に無いユーザー作成API・招待UI（SCR-070拡張）・Cognito AdminCreateUser連携
  （task roleへ `cognito-idp` 権限追加）を新規に作る**ことになり、影響が大きい。
  それでいて教育用サービスの性質（実決済・実顧客情報を扱わない）に対して過剰である。
- 選択肢3は無効側を選んだときの登録手段が未実装のままになり、
  「切り替えられるが片方は動かない」設定が増えるだけで判断の先送りにしかならない。

## 追加するガード

JITそのものは許容するが、JITは「トークンさえ通れば利用者が増える」経路なので、
**トークンの受入条件を明示的に狭める**。

| # | ガード | 理由 |
|---|---|---|
| 1 | `token_use == "access"` を検証する | CognitoはIDトークンとアクセストークンを**同じissuer・同じJWKSで発行する**ため、署名とissuerの検証だけでは区別できない。IDトークンは利用者本人向けの身元情報であり、API呼出しの認可根拠にしない |
| 2 | `client_id` を許可リストで検証する | 同一User Poolに別のアプリクライアントを追加しても、許可したクライアント発行のトークンだけを受理する。`ecs.tf` が `CF_IDENTITY_COGNITO_ALLOWED_CLIENT_IDS` へ Webクライアント ID を注入する。未設定（local/test）では検証しない |
| 3 | JITで付与するロールは SUPPORTER 固定 | 昇格は既存の API-AD-002（ロール更新・ADMIN専用・監査対象）を必ず通す |
| 4 | JIT登録を監査ログへ記録する（`USER_JIT_PROVISION`） | 「誰がいつ自動登録されたか」を後から追えるようにする。source は `SYSTEM` |

### プロフィールはプレースホルダで作る

**Cognitoのアクセストークンには `email` / `name` クレームが無い**（IDトークン専用）。
ガード1でアクセストークンのみを受理するため、JIT時に本人の氏名・メールは取得できない。

したがって `app_user` は次のプレースホルダで作成し、本人に API-US-002（プロフィール更新）で
埋めてもらう前提とする。

| 項目 | 値 |
|---|---|
| `email` | `<cognito_subject>@cognito.invalid`（RFC 6761 の予約TLD。誤送信しない） |
| `display_name` | `(未設定)` |

変更前の実装はトークンから `email` / `name` を読もうとし、取れなければ暗黙にフォールバック
していた。**アクセストークンでは必ずフォールバックする**ため、取得できるかのような実装を
やめ、プレースホルダであることを明示する。

## 影響

- `CognitoJwtAuthenticationConverter` はトークン検証と変換に徹し、登録処理は
  `JitProvisioningService`（application層）へ移した。監査記録もそこで行う。
- 同一Subjectの同時初回アクセスは `uq_app_user_cognito_subject` により片方が失敗するため、
  `DuplicateKeyException` を捕捉して既存行を読み直す。
- 未検証のプロフィールで支援申込まで到達しうる。支援フローが実名・連絡先を要求する場合は、
  プロフィール未設定を検出して入力を促す画面側の制御が別途必要になる（本ADRの範囲外）。

## 残る前提

`allow_admin_create_user_only = false` を維持する。将来これを `true` にする場合は、
選択肢2の実装一式（ユーザー作成API・招待UI・AdminCreateUser連携）が必要になるため、
本ADRを差し替えること。
