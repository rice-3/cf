## 1. このサービスの技術要件

クラウドファンディングは**他人の金銭を預かり、条件成立時に事業者へ渡し、不成立時に返す**サービスである。
技術選定はこの性質から逆算している。

| # | 業務上の性質 | そこから来る技術要件 |
|---|---|---|
| R1 | 支援・決済・返金で**金銭が動く** | 二重課金・二重返金を構造的に起こさない。金額と状態の整合を常に保つ |
| R2 | 決済事業者との連携が**非同期**（Webhook） | 「決済は成立したがこちらに記録が無い」を作らない。重複受信に耐える |
| R3 | 募集期間・目標金額で**締切判定**がある | 期限到来の一括処理が確実に1回だけ走る |
| R4 | 起案者・支援者・審査者・運用者・管理者・監査者が**同一システムを別権限で使う** | ロールごとの認可を漏れなく効かせる |
| R5 | 金銭と個人の操作履歴を**後から立証**する必要がある | 改ざんされない監査証跡を長期保持する |
| R6 | 一般公開されるWebサービス | 外部からの攻撃面を最小化する。障害を検知して復旧できる |
| R7 | 継続的に機能追加する | 変更が既存の業務ルールを壊さないことを機械的に検査する |

**現時点の到達点**: 業務フローは一気通貫で動作し、CI/CD・IaC・監視定義まで整備済み。
未了は実AWS環境での構築・疎通と、決済事業者・SESの実接続（§5、§6）。

## 2. アーキテクチャの中核判断

### 2.1 モジュラーモノリス（単一デプロイ単位）

コンテキスト（identity / project / review / funding / payment / notification / file / audit / shared）を
**パッケージで分離し、単一プロセスでデプロイする**（ADR-0001）。

| メリット | 内容 |
|---|---|
| **分散トランザクションを持ち込まない** | 支援作成・在庫予約・Outbox書込が**同一DBトランザクション**で完結する。マイクロサービスなら Saga と補償トランザクションが必要になる領域 |
| 運用点が少ない | デプロイ対象・監視対象・障害切り分け対象が1つ。少人数の運用に耐える |
| 境界は維持される | ArchUnitで依存方向とコンテキスト間の公開契約を**機械的に強制**するため、分割が必要になった時点で切り出せる |

**トレードオフ**: 単一プロセスなので特定機能だけスケールできない。単一DBが上限になる（§5.3）。

### 2.2 Transactional Outbox

業務更新とイベント発行を**同一トランザクションで書き込み**、別プロセス（Worker）が配送する。

これが解決するのは **R2** である。「決済要求は出したがDBには残っていない」「DBは更新したが後続処理が走らない」
という**二重書き込み問題**を、DBのトランザクション保証だけで閉じる。

配送先は**アプリ内Handler**とした（ADR-0008）。単一Backendプロセスでは購読側が同一JVMにあり、
SQSを挟んでも「Worker → SQS → 同一アプリのポーラー → 同じHandler」となって分離の利得が出ない一方、
at-least-once の重複対処・DLQ運用・ローカル検証環境のコストは実在するため。

> Workerを別サービスへ切り出す / アプリ外の購読者が増える / 配送がAPIレイテンシを圧迫する、
> のいずれかが起きた時点でSQS化する（条件をADR-0008に明記）。

### 2.3 金銭整合を守る4つの仕掛け（R1・R3）

いずれも**アプリのロジックではなくDBの制約・ロックで担保**している。実装バグや再送では破れない。

| 仕掛け | 実装 | 防いでいる事故 |
|---|---|---|
| **冪等制御** | `idempotency_record`（PK: scope + actor_id + idempotency_key）。request_hash相違は409 | 通信再送・二重クリックによる**二重支援** |
| **条件付きUPDATE + 楽観ロック** | `reward_plan` の在庫予約を「上限を超えない」条件付きUPDATEで行い、version競合時は1回再試行 | リターン枠の**売り切れ超過** |
| **部分一意インデックス** | `uq_refund_active_support on refund (support_id) where status <> 'FAILED'` | イベント重複配送による**返金の二重作成**（恒久失敗後の再作成は許可） |
| **分散ロック（ShedLock）** | BAT-001/002/004/005/007/008/009/010 に付与（ADR-0003） | 複数インスタンスでの**バッチ二重起動による二重返金・重複通知** |

> Outbox配送（BAT-006）だけはShedLockを**意図的に外している**。`FOR UPDATE SKIP LOCKED` による
> 競合コンシューマ設計であり、複数インスタンスが並行処理するのが正しいため。

### 2.4 契約ファースト

実装から OpenAPI spec を生成し、フロントの型を spec から生成する。CIで**両方の鮮度をゲート化**している。

- `OpenApiSpecIntegrationTest`: 実装とコミット済み spec の一致を検証
- `ci.yml`: `npm run gen:api-types` の実行漏れを検出
- `openapi.yml`: `oasdiff breaking` で**破壊的変更を検出しCIを落とす**

これで **R7** の一部（API変更が既存クライアントを壊さない）を機械的に担保している。

| **Kotlin** | 2.4.10 | null安全と `sealed class` により、**状態遷移と業務ルールを型で表現**する。支援状態9種・決済状態の遷移が実行時ではなくコンパイル時に守られる |

| **Spring Data JPA / Hibernate** | 同梱 | `ddl-auto: validate` により、**Flyway管理のスキーマとEntityの不一致を起動時に検出**する。本番でのカラム型不一致による実行時エラーを防ぐ |

### 3.4 セキュリティ・監査

| 施策 | 実装 | 解決すること |
|---|---|---|
| **トークン受入条件の限定** | `token_use == "access"` と `client_id` の検証（ADR-0007） | Cognitoは**IDトークンとアクセストークンを同一issuer・同一JWKSで発行**するため、署名検証だけでは区別できない。IDトークンの持ち込みを塞ぐ |
| **内部向けパスの外部遮断** | ALBリスナールールで `/actuator*` を全環境、`/swagger-ui*`・`/v3/api-docs*` を dev 以外で404（ADR-0004相当・§2.4） | 運用情報とAPI仕様の外部露出を防ぐ。**アプリ側でも無効化する多層防御** |
| **最小権限のDBユーザー** | `cf_app_rw`（DMLのみ、DDL不可）+ ログインユーザー分離 | アプリ経由でのスキーマ破壊を防ぐ。**切替は未適用**（§5.1） |
| **監査アーカイブの改ざん防止** | タスクロールは `s3:PutObject` のみ。読み直せないため**PUTにSHA-256を添えてS3側に検証させる**（ADR-0009） | **R5**。アプリ経由での改ざん・削除が構造的に不可能 |
| **CD権限の限定** | GitHub OIDC の `sub` を `environment:{dev,staging}` に限定 + Environment保護（main限定・承認者必須） | 任意ブランチからの本番反映を防ぐ |
| **サプライチェーン検査** | Trivy（依存・コンテナ）/ CodeQL / Semgrep / gitleaks | 既知脆弱性と秘密情報混入の検出 |

## 4. 品質を担保する仕組み

変更が業務ルールを壊さないこと（**R7**）を、**守備範囲の異なるゲートの重ね掛け**で担保している。

| 層 | 手段 | 検出するもの |
|---|---|---|
| 型 | Kotlin / TypeScript | 状態・契約の不整合 |
| 静的解析 | ESLint / Semgrep / CodeQL | 実装上の危険パターン |
| **構造** | **ArchUnit** | **依存方向違反・コンテキスト境界の侵食**。レビュー依存だと必ず漏れる領域を自動化 |
| 振る舞い（単体） | JUnit 5 / Kotest / MockK | ドメインロジック |
| 振る舞い（結合） | **Testcontainers（実PostgreSQL 18）** | `FOR UPDATE SKIP LOCKED`・部分一意インデックスなど**DB固有の挙動**。インメモリDBでは検証できない |
| 振る舞い（E2E） | Playwright | 画面〜APIを跨いだ回帰 |
| 契約 | `oasdiff breaking` | API破壊的変更 |
| 供給網 | Trivy | 修正可能なHIGH/CRITICAL |

**Testcontainersで実DBを使う判断が特に効いている。** §2.3 の整合性担保はPostgreSQL固有機能に
依存しており、H2等では検証できない。実際に「重複配送でも返金が二重作成されない」ことを結合テストで確認している。

## 5. 懸念事項

### 5.1 本番稼働前に解消が必要

| # | 懸念 | ビジネス影響 | 現状 |
|---|---|---|---|
| 1 | **監視パイプラインが未配線** | `/actuator/prometheus` は公開済みだがCloudWatchへ発行するCollectorが無く、**業務滞留・バッチ停止・返金失敗のアラートが発火しない**。障害に気付けない | ADOTサイドカー構成を手順書 §17 に確定済み。apply時に実施 |
| 2 | **決済事業者が未接続** | 現在はSandboxアダプタ。**実売上が立たない** | `PaymentGatewayPort` で抽象化済みでアダプタ差し替えで対応可能。署名検証・Webhook受信・重複排除の枠組みは実装済み |
| 3 | **SESがサンドボックス状態** | 検証済みアドレスにしか送れず、**一般利用者へ通知が届かない** | Production access 申請が必要（最大24時間） |
| 4 | **最小権限DBユーザーが未適用** | アプリが**DDL権限を持つオーナー接続のまま**。SQLインジェクション等が発生した場合の被害が拡大する | ロール定義とTerraform配線は完了。切替は3手順（ロール作成→Secret投入→2行変更）で、順序厳守 |
| 5 | **実AWS環境での未検証** | apply・疎通・`desired_count > 1` でのShedLock実機動作・監査アーカイブの実出力が未確認 | 手順は確定済み。AWS契約後 |
| 6 | **性能試験が未実施** | 同時支援・締切集中時の挙動が未知。**募集終了直前のアクセス集中はこの業務の典型的なピーク** | 負荷試験ツールは選定のみで未導入 |

### 5.2 継続的に管理が必要

| # | 懸念 | 内容 |
|---|---|---|
| 7 | **Trivyゲートが恒常的に赤い** | `postcss` CVE-2026-45623。`next@16.2.12` もまだ `postcss@8.4.31` 固定で上流待ち。**赤が常態化すると新規の本物のHIGHを見逃す**ため、ゲートの色ではなくSARIFの中身で確認する運用にしている |

| 9 | **CodeQLがKotlin 2.4未対応** | Semgrepで代替中。JVM側SASTの精度が本来より低い |
| 10 | **先行バージョン採用の副作用** | Corretto 25 / Kotlin 2.4 / Spring Boot 4.1 / Next 16 / React 19 / PostgreSQL 18。**周辺ツールが追随しない事例を既に3件踏んでいる**（#8・#9 とJavaフォーマッタ）。今後も発生する前提で、回避策と復旧条件を記録する運用にしている |

### 5.3 設計上のリスク

| # | 懸念 | 内容 |
|---|---|---|
| 11 | **プロファイル別設定ファイルが無い** | dev以上は `application.yml` ＋ ECS環境変数のみ。**「本番では無効化する」とコメントされた設定が、環境変数で明示上書きしない限り有効のまま**になる。実際にSwagger UIの公開で顕在化した |
| 12 | **環境変数の不整合が「無言の既定値」になる** | 束縛されない環境変数は起動を止めず既定値で動く。**設定突き合わせを実施するまで4件潜伏していた**（SES設定セット未束縛、S3キー接頭辞が全環境同一など）。IaCに変数を足すだけでは機能しない |
| 13 | **単一DB・単一プロセスがスケール上限** | 支援集中時に**DBが先に飽和する**。読み取りレプリカ・キャッシュ・機能分割のいずれも未着手 |
| 14 | **監査アーカイブの参照手順が未整備** | 書き込み専用にした結果、**運用者がどの権限でどう取り出すかが決まっていない**。紛争対応時に困る |
| 15 | **JIT登録のプロフィールがプレースホルダ** | アクセストークンに `email`/`name` が無いため仮値で作成し、本人に更新させる前提。**支援時に実名・連絡先が必須なら、入力を促す画面制御が別途必要** |
| 16 | **CD承認の自己承認が可能** | Environment承認者が1名のため `prevent_self_review = false`。**起票者が自分で承認できる** |

## 6. 今後の課題

優先度は「本番稼働への必須度 × 事故時の影響」で付けている。

### 6.1 稼働前に必須

| # | 課題 | 内容 |
|---|---|---|
| 1 | **監視パイプラインの構成と発火確認** | ADOTサイドカーを配置し、**アラートが実際に飛ぶところまで**確認する。ここが無いと障害検知できない |
| 2 | **決済事業者の選定と接続** | `PaymentGatewayPort` のアダプタ実装。Webhook署名方式・返金API仕様・照合手順の確認。**テスト環境での二重課金/返金試験は必須** |
| 3 | **DB接続分離の切り替え** | ロール作成 → Secret投入 → 2行変更 → apply。**順序を誤ると起動不能**になるため手順どおりに |
| 4 | **SESサンドボックス解除** | Production access 申請。バウンス・苦情の受信と送信抑止の実装も併せて（現状は構成セットのみ） |
| 5 | **性能試験** | 募集終了直前のアクセス集中と同時支援を想定した負荷試験。**在庫予約の競合とバッチの処理時間**を実測する |
| 6 | **障害復旧手順の実地確認** | RDSスナップショットからの復元、タスク異常時の切り離し、Outbox滞留時の復旧をリハーサルする |

| 9 | **監査アーカイブの参照手順整備** | 権限設計と取り出し手順を `runbook.md` へ |
| 10 | **CD承認者の追加と自己承認の禁止** | 承認者を増やし `prevent_self_review = true` へ |

## 7. 総括

**金銭を扱うサービスとして要求される整合性を、アプリケーションロジックではなく
DBの制約・ロックとトランザクション境界で担保している点が、この構成の中核である。**
二重支援・在庫超過・返金二重作成・バッチ二重起動の4つを、それぞれ冪等キー・条件付きUPDATE・
部分一意インデックス・分散ロックで塞いでおり、実装バグや通信再送では破れない。

モジュラーモノリスの選択により分散トランザクションを回避しつつ、ArchUnitで境界を機械的に
維持しているため、**将来の分割余地を残したまま現在の運用コストを低く保てている**。

一方で、**本番稼働にはまだ到達していない**。特に監視パイプライン未配線（障害を検知できない）と
決済事業者未接続（売上が立たない）は稼働の前提条件であり、性能試験の未実施は
募集終了直前という**この業務固有のピーク**に対して未知数を残している。

設計上の最大のリスクは §5.3 の #11・#12 で、いずれも「間違っていても動いてしまう」種類である。
既に4件の潜伏不整合を生んでおり、プロファイル別設定ファイルの導入（課題 #7）を推奨する。
